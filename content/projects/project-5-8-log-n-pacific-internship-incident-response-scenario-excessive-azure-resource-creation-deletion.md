## Introduction

During this stage of my internship with LOG(N) Pacific, I focused on detecting and investigating anomalous Azure resource lifecycle operations using Microsoft Sentinel. This scenario simulated a condition where an identity performs an unusual number of resource creation (WRITE) or resource deletion (DELETE) events within a short time window. Such patterns are highly relevant in real enterprise environments because they may indicate unauthorized automation, compromised service principals, rogue provisioning scripts, or even malicious abuse of cloud resources.

The investigation was driven entirely by telemetry from the AzureActivity table, streamed into the Log Analytics Workspace that powers Microsoft Sentinel. The goal of the scenario was to build a scheduled detection rule that identifies any Caller who performs five or more successful WRITE/DELETE operations while excluding Sentinel-related administrative operations. After creating the analytics rule, I triggered the scenario by repeatedly creating and deleting virtual machines to populate the activity logs with the necessary events. The remainder of the workflow followed the NIST 800-61 incident response process.

## Detection Engineering and Rule Deployment

The first step was validating that AzureActivity logs were flowing correctly into the workspace. Running a baseline activity query surfaced normal subscription activity, confirming that the ingestion pipeline was functioning. This baseline verification is shown in the Azure Logs interface below.

With telemetry confirmed, I implemented the detection logic to identify Caller identities that exceeded the WRITE/DELETE activity threshold. The query output returned multiple identities with high creation and deletion counts, including several Callers performing upwards of twenty resource operations within the last 24 hours. The results validated that the environment contained sufficient activity to test the detection rule.

Once the logic was tested, I configured the scheduled rule in Sentinel. In the rule creation wizard, I defined the name, severity, and MITRE ATT&CK mappings representing the potential impact of destructive cloud operations. Sentinel's rule builder captured the logic exactly, set to execute every four hours over a seven-day lookup period.

Entity mapping was configured to allow Sentinel to tie together ObjectIdentifier values (Azure AD SIDs) and Caller IP addresses. This mapping is essential for enabling the investigation graph to visualize relationships during analysis.

The final review step confirmed that the rule was validated successfully and ready for deployment.

## Incident Creation and Triage

Within minutes of saving the rule, Sentinel generated a new incident titled "Samson – Excessive Resource Creation or Deletion." The incident included one alert and more than two hundred correlated AzureActivity events, confirming that the scheduled rule had successfully identified the excessive operations.

I assigned the incident to myself and moved it into Active status to begin the formal triage process.

## Investigation and Activity Reconstruction

The Sentinel investigation graph highlighted a significant number of entities connected to the alert, including more than 200 IP addresses and over 140 distinct account references. This density is expected in large Azure environments where shared resource groups, automation accounts, and background processes interact with cloud assets.

To understand the activity of the relevant Caller, I pivoted into Log Analytics to analyze the resource operations generated by the primary ObjectIdentifier surfaced by the rule. The identity 5deb2a08-7269-47d6-896b-8bc52d396466 stood out, associated with the IP address 4.153.100.136. Reconstructing the event trail showed this Caller repeatedly performing resource subgroup operations, primarily WRITE and DELETE actions, across multiple STUDENT-RG resource groups.

The targeted query revealed consistent patterns of VM provisioning, network rule creation, and resource group deletions. These operations were executed successfully and in rapid sequence, which is characteristic of automated orchestration rather than manual misuse.

<InlineGallery images={excessive-azure-resource-investigation} title="Investigation and Incident Closure" />

The repetition and uniformity of these actions strongly indicated legitimate lab automation behavior, not malicious exploitation or unauthorized access.

## Incident Classification and Closure

After reconstructing the user's activity, validating the telemetry, and reviewing the Caller's operational patterns, the event was confirmed to be harmless and expected within the cyber-range environment. The excessive operations originated from normal platform automation accounts responsible for provisioning and destroying ephemeral training resources.

No indicators of compromise or privilege abuse were detected throughout the investigation. There were no unexpected resource types, no suspicious IP pivots, and no deviation from standard lifecycle actions.

The incident was therefore documented and classified as a Benign Positive, tied to expected platform behavior rather than an actual threat. The final comment added to the incident captured the findings:

"Reviewed excessive resource creation/deletion activity associated with ObjectIdentifier 5deb2a08-7269-47d6-896b-8bc52d396466 from IP 4.153.100.136. Investigation confirmed thousands of legitimate WRITE/DELETE operations tied to automated resource lifecycle actions within the cyber-range lab. No indicators of compromise, unauthorized access, or abnormal privilege usage were identified. Activity is consistent with expected system-driven provisioning/deprovisioning. Classifying as Benign Positive and closing the incident."

With documentation complete, the incident was closed, concluding the analysis.

## Conclusion

This project reinforced the importance of robust cloud activity monitoring, especially in environments where resource creation and deletion occur at scale. AzureActivity logs play a critical role in detecting unusual provisioning patterns, and Sentinel's analytics engine provides an effective layer for identifying potential misuse. While the alert in this case was benign, the workflow demonstrates how cloud misconfigurations, compromised automation accounts, or rogue provisioning scripts can be surfaced quickly when detection rules are properly engineered.
